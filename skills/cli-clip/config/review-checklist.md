# レビューチェックリスト ─ セルフレビュー（ブラインド）で必ず見る観点

レビュアー（サブエージェント）には **このファイルと config/persona.md と対象物だけ**を渡す。
台本を書いた側の文脈は渡さない（ブラインド）。レビューは各段階 **1回**。指摘を取り込んだら次へ進む。
指摘の書式: `[対象id or 行] 観点 → 指摘 → 直し方の案`。褒め言葉は書かない。

## A. Phase 1 前 ─ あらすじレビュー（対象: clips/<id>/research.md の「あらすじ」）
- [ ] A1 「知らないとどう困るか」が一文で書けているか
- [ ] A2 1本に操作が1つだけか（混ざっていたら分割を提案）
- [ ] A3 状況→操作→結果の3行で、初心者が「押す前と後の違い」を想像できるか
- [ ] A4 デモ題材は、初心者が実際にやりそうな頼み方か（開発者っぽい題材になっていないか）
- [ ] A5 見せ場の画面（実録で必ず取る状態）が具体的に指定されているか
- [ ] A6 持ち帰り（1つ）が、操作の説明ではなく「安心」や「できること」になっているか
- [ ] A7 練習フォルダで完結するか。実データ・実リポジトリを映さないか

## B. Phase 2 ─ 台本レビュー（対象: clips/<id>/clip.json）
- [ ] B1 説明スライド: 一文＋補足2つまで。文字が多くないか。用語は平易か
- [ ] B2 ナレーション: ですます調・断定なし・二人称なし・比喩や励ましなし
- [ ] B3 用語: 開発用語が説明なしに出ていないか（config/terms.tsv）。操作名は初出で一言添えているか
- [ ] B4 d1 で「何を頼んだか」を最初に言っているか
- [ ] B5 d2 の見せ場で、押したキー／打ったコマンドと、画面の反応が対応しているか
- [ ] B6 d3 で「何が変わっていないか」「次に何をすればよいか」が伝わるか。d4 が要るか（§4.3）
- [ ] B7 各カットの右パネル（cap／prompt／note／badge）がナレーションと同じ語を使っているか
- [ ] B8 端末の行（S）は transcript.md と一致しているか（原文ママ。追加・改変なし）
- [ ] B9 尺: 1〜2分に収まる見込みか。長ければ「説明を増やす」ではなく「操作を割る」提案になっているか
- [ ] B10 最後の一文で終わって違和感がないか（エンディングなし）

## C. 人のレビューで出た指摘（蓄積。Phase 4 で追記する）
> 書式: `- YYYY-MM-DD <clip id> <カット>: 指摘の要点 → 次回から見る観点`
> ここに溜まった観点は、次回以降の A／B のレビューで必ず見る。
